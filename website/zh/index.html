使用场景

以下只是部分示例。您可以使用系统中的标识符、字段、关键词或时间范围，调查所需的 Kafka 消息。 尤其适合已将业务运行数据保存在 Kafka 中，但不需要承担整套 ELK 部署成本和维护负担的独立开发者与小型团队。

订单调查

客户已付款，订单为什么还卡着？

在订单、支付和处理主题中依次搜索同一个订单 ID，无需为每个主题编写临时 Consumer。

  1. 01找到等待库存的订单
  2. 02确认支付已获授权
  3. 03定位仓库系统超时
实际应用演示 · 模拟数据 · 28 秒
搜索键 ORD-20260812-483921

调查结果 支付成功，但库存预留失败，错误为 WAREHOUSE_TIMEOUT。

保存在 Kafka 中的 Web 与应用日志

无需部署 ELK，即可搜索 Kafka 中的日志。

如果 Nginx 和应用日志已收集到 Kafka，可在本地建立索引，缩小故障时间范围，再沿 trace ID 追踪原因。

  1. 01从 10 万条 Nginx 日志中筛选 checkout 的 502 错误
  2. 02缩小到故障时间段
  3. 03通过 trace ID 追踪应用日志
实际应用演示 · 模拟数据 · 35 秒
高级搜索 P.status = "502*" AND P.path = "/api/checkout*" AND P.method = "POST*"

调查结果 checkout 服务的支付连接池已耗尽： 50 / 50 个连接正在使用，184 个请求等待中。

观察符合条件的消息

及时发现新出现的支付失败。

Kaflow Search 持续同步主题时，支付运维人员可通过轻量的关键词 Watch 观察所需消息。

  1. 01Watch 关键词： payment_failed
  2. 02保持支付主题自动同步
  3. 03打开新匹配的消息并处理原因
实际应用演示 · 模拟数据 · 27 秒
Watch 关键词 payment_failed

新匹配消息 订单 ORD-20260819-WATCH03 因支付网关在 3000 毫秒后超时而失败。

Kafka 故障期间的调查

Kafka 不可用时，也能继续调查。

利用最后保存的本地索引查看故障前收集的消息，找出仍需人工处理的任务。

  1. 01检查断开连接前的处理流程
  2. 02继续搜索本地索引
  3. 03找到最后一笔需要人工审核的订单
实际应用演示 · 模拟数据 · 49 秒
本地索引搜索 PENDING

调查结果 支付已获授权，但履约尚未开始。订单状态仍为 PENDING ，需要人工审核。
