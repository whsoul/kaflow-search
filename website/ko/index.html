아래 사례는 시작점일 뿐입니다. 시스템에 맞는 식별자, 필드, 키워드 또는 시간 범위로 필요한 Kafka 메시지를 조사할 수 있습니다. 운영 데이터를 Kafka에 보관하고 있지만 ELK 스택 전체를 운영하는 비용과 부담까지는 필요하지 않은 개인 개발자와 소규모 팀에 특히 유용합니다.

주문 조사

결제는 끝났는데 주문은 왜 멈췄을까요?

토픽마다 임시 Consumer를 만들지 않고 같은 주문번호를 주문, 결제, 처리 토픽에서 차례로 검색하세요.

  1. 01재고를 기다리는 주문 확인
  2. 02결제 승인 여부 확인
  3. 03창고 시스템 타임아웃 발견
실제 제품 데모 · 가상 데이터 · 28초
검색 키 ORD-20260812-483921

확인 결과 결제는 성공했지만 재고 예약이 WAREHOUSE_TIMEOUT으로 실패했습니다.

Kafka에 저장된 Web/WAS 로그

ELK 없이 Kafka에 쌓인 로그를 검색하세요.

Nginx와 애플리케이션 로그가 Kafka에 수집되고 있다면 로컬에 인덱싱하고 장애 시간대를 좁힌 뒤 trace ID로 원인을 추적할 수 있습니다.

  1. 01Nginx 10만 건에서 checkout 502 필터링
  2. 02장애 시간대로 범위 좁히기
  3. 03trace ID로 애플리케이션 로그 추적
실제 제품 데모 · 가상 데이터 · 35초
상세검색 P.status = "502*" AND P.path = "/api/checkout*" AND P.method = "POST*"

확인 결과 checkout 서비스의 결제 연결 풀이 고갈됐습니다. 50 / 50 사용 중, 184건 대기.

조건 기반 트래픽 Watch

결제 실패가 들어오는 순간 확인하세요.

Kaflow Search가 토픽을 동기화하는 동안 결제 운영 담당자는 가벼운 키워드 Watch를 열어둘 수 있습니다.

  1. 01payment_failed Watch 설정
  2. 02결제 토픽 자동 동기화
  3. 03새 일치 메시지를 열어 원인에 대응
실제 제품 데모 · 가상 데이터 · 27초
Watch 키워드 payment_failed

새 일치 메시지 주문 ORD-20260819-WATCH03이 결제 게이트웨이 3000ms 타임아웃으로 실패했습니다.

Kafka 장애 상황에서도 조사 지속

Kafka가 응답하지 않아도 조사를 계속하세요.

마지막 로컬 인덱스로 장애 직전까지 수집한 메시지를 확인하고 수동 처리가 필요한 작업을 찾을 수 있습니다.

  1. 01연결 중단 직전 처리 흐름 확인
  2. 02로컬 인덱스에서 검색 계속
  3. 03수동 검토가 필요한 마지막 주문 발견
실제 제품 데모 · 가상 데이터 · 49초
로컬 인덱스 검색 PENDING

확인 결과 결제는 승인됐지만 주문 처리가 시작되지 않았습니다. 주문은 수동 검토가 필요한 PENDING 상태입니다.
