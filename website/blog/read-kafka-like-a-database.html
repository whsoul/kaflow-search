Read Kafka like a Database

Building a local index so a Kafka topic can be queried directly.

I have used Kafka for years — user action traces, event sourcing propagation, pipeline steps. Every time, the same things followed it. Elasticsearch and Logstash and Kibana, so that someone could find a message. A sink connector, so the data could be queried. ksqlDB, so it could be counted.

One afternoon I was looking for a single trace event. I knew it was in a topic. I knew roughly when it happened. And to get at it I was expected to stand up a search cluster.

The machine I was typing on was idle except for a browser.

The stack you end up running

To search messages you operate Kafka Connect (or Logstash) into Elasticsearch, a sink connector into a database, and ksqlDB or Flink for counting. Each one is a service that has to be up, upgraded and paid for, and each is read through a different client.

예시

None of it was hard, exactly. The connector config took a day. The index mapping took another, and then again every time a field changed shape. Disk on the search nodes needed watching, and its retention never quite matched the topic's, so the answer to "is it still there" depended on which system you asked.

None of that work was about finding messages. It was about keeping the thing that finds messages alive.

What makes a local index possible

A Kafka topic is append-only, ordered within a partition, and addressable by offset. An index over it is therefore a pure function of (topic, partition, offset range) — it can be built incrementally, and resumed from wherever it stopped, without coordinating with anything else.

The index itself lives in RocksDB — the same embedded store Kafka Streams keeps its state stores in, and ksqlDB with it. Putting a RocksDB index next to a consumer is not a new idea in this ecosystem. The only thing that changes here is which machine the consumer runs on.

Where to put the index

Three embedded stores could carry this, and choosing between them is a trade rather than a ranking. Each gives something away.

Good atCosts youPick it when
SQLite B-tree, FTS5 full-text search with ranking; substring matching through the trigram tokenizer a trigram index runs several times a word index; B-tree inserts turn random once it outgrows memory; reclaiming trimmed space rewrites the file the data fits comfortably
DuckDB columnar SQL over large data, LIKE '%…%' included answers by scanning, so cost tracks the topic rather than the hits; trimming the oldest rows rewrites data the answer is an aggregate
RocksDB LSM tree sustained writes and cheap bulk deletion at volume matching is yours to build — tokenizing and n-grams both the data keeps growing

The last column is the short version. Each store can be pushed past it; these are the conditions under which it is not a fight.

None of this makes the other two bad at their jobs. DuckDB would beat an LSM store outright at the one thing this tool also does with the index — bucketing messages by time for a chart — because columnar aggregation is what it is for. It loses on the other three demands, which happen to be the ones that run constantly.

All three are workable routes, and for a few hundred thousand entries the first one is the easy answer. Kaflow takes the third for the reason ksqlDB does: it is shaped like the way Kafka data arrives, append after append with the oldest expiring first, and the trimming policies further down need slices removed in bulk without rewriting what stays.

The bill for that comes due in the third column. Deriving terms, keeping them ordered, and matching against them are written rather than taken off the shelf — most of the work in this tool sits there. The schema those terms use is out of scope here.

It also sets the shape of what can be asked. A sorted key store answers equals this and starts with this by seeking, and nothing else comes for free: matching words inside a sentence means tokenizing before you write, and matching part of a word means an n-gram index — a second index with a size of its own, since an eight-letter word is one token but six trigrams.

Kaflow does the first and not the second. Values are indexed whole, and fields marked for it are also split into words, so a term in the middle of a free-text field is found by seeking rather than scanning. What is not there is %oo% — matching part of a word. For an order id, a trace id, a key or a word in a message that has never been the question; for a partial token it is, and a scan still wins there.

Doing it on the laptop instead

Fetch by explicit partition and offset, build the index locally, search it locally. No consumer group is joined and no offsets are committed, so the cluster does not notice.

인덱싱이 실제로 어떻게 도는지. key/value 파싱 → 항목 생성 → 저장 → 조회. 키 스키마 같은 내부는 개념 수준까지만.

예시 — 사실관계는 확인하고 쓰세요

For each message the tool reads the key and the value, decodes them in whatever format the topic turned out to be in, and walks the result. Every scalar it finds becomes a term: the path it sat under, and its value. Each term is written down with the (partition, offset) it came from.

That is the whole index — a sorted map from term to positions, plus one small record per message holding what a result row needs to show. Nothing else is kept.

Scanning versus looking up

Without an index there is only one way to find a message: scan the topic and filter client-side. The work is proportional to the topic, not to the answer — two matches in two million messages still costs two million reads across the network, and refining the query costs them again.

An index inverts that. Terms are stored in sorted order, so a prefix seek lands directly on the block that matches and reads nothing on either side of it. Each entry carries a (partition, offset) and enough to render a row, so the whole result list is built without asking the cluster for anything — zero reads, however many times the query is refined. Indexing pays the full pass once, up front; everything after it is proportional to the number of hits.

Opening a row is the only thing that goes outward, and it asks for exactly one message by (partition, offset) — the raw payload and any field that was not indexed. No consumer group is joined and no offsets are committed, so no rebalance is triggered and nobody else's position moves.

The one pass you have to make

None of this is free. Before the first search there is a full pass over the topic — the same read that scanning would have done, except it happens once instead of on every query. That is the honest cost of the approach, and it is worth being precise about what it does and does not involve.

You do not describe the data

Picking a topic samples its messages, classifies the wire format, and ranks which fields are worth indexing. There is no mapping to write, no schema to register and no connector config — the parts of a pipeline that usually cost more than the infrastructure itself.

It is quicker than the pipeline it replaces

And it is not repeated

The last indexed offset is recorded per partition, so nothing is ever read twice. Leave a topic on manual and it catches up in one step the next time you pick it or press sync; turn on autoSync and it keeps up in slices while the app is open. Either way the full pass happens once, and an interrupted one resumes where it stopped rather than starting over.

No comparison to the Kafka-side size is given. The same messages occupy wildly different numbers of bytes on a broker depending on producer compression and batching, so it is not a stable baseline. What is reported here is what the local disk actually holds, after RocksDB's compression.

Both rows come from one JSON topic. A different serialization format, or a topic with far more fields, will move these numbers.

The last three rows are the honest part. If you need to match part of a word, if a team has to share one view, or if the data must outlive Kafka's retention, the pipeline is the right answer. A local index trades those three away to get everything above them.
